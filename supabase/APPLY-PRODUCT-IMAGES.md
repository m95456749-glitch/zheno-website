# اجرای کنترل‌شدهٔ مدیریت تصاویر ژینو — ممیزی نهایی نسخهٔ ۲

## روش پیشنهادی جدید: بدون کپی SQL، از GitHub Actions

مسیر **manual-only با تست، plan و apply تأییدشده** آماده شده است؛ راهنمای دقیق Secret/Variable و اجرا در [RUN-PRODUCT-IMAGES-ACTIONS-FA.md](RUN-PRODUCT-IMAGES-ACTIONS-FA.md) قرار دارد. فقط Secret محیط `SUPABASE_DB_PASSWORD` و دو Variable به نام‌های `SUPABASE_PROJECT_REF` و `SUPABASE_DB_HOST` لازم‌اند؛ Access Token یا service_role لازم نیست.

این مسیر تاریخچهٔ baseline را الزامی می‌داند، seed/v1 ثبت‌نشده را بازپخش نمی‌کند و تنها فایل کامل v2 را اعمال می‌کند. هیچ workflow یا SQL روی Remote در این تحویل اجرا نشده است؛ تغییرات هنوز commit/push نشده‌اند. **دستور SQL Editor زیر صرفاً روش جایگزین دستی قبلی است، نه پیش‌نیاز اجرای Actions.**

## حکم اجرا

**SQL برای schema منطبق با migrationهای این مخزن، آمادهٔ اجرای کنترل‌شده است؛ تأیید بی‌قیدوشرط دیتابیس Remote نیست.** نصب مستقیم روی کاتالوگ اولیه، ارتقا از گالری نسخهٔ ۱ و اجرای مکرر در PostgreSQL محلی آزموده شده‌اند. schema، Auth، Storage ابری و رقابت چند connection روی پروژهٔ واقعی بررسی اجرایی نشده‌اند.

اشکال مسدودکنندهٔ شناخته‌شده‌ای در مسیرهای آزموده‌شده باقی نمانده است. با این حال **بدون backup قابل بازیابی و هماهنگی با نسخهٔ جدید پنل، اکنون روی production اجرا نکنید.** نسخهٔ قدیمی که مستقیم در جدول می‌نویسد بعد از این migration دیگر امکان مدیریت تصاویر ندارد. انتشار کد نیازمند تأیید جداگانهٔ شماست و انجام نشده است.

## روش جایگزین: اجرای یک‌جای SQL در SQL Editor

پیش‌شرط: backup قابل بازیابی از دیتابیس و فایل‌های مهم Storage داشته باشید؛ هنگام اجرا نوشتن مدیران در محصولات/گالری را موقتاً متوقف کنید و زمان اجرا را با انتشار مورد تأیید نسخهٔ جدید پنل هماهنگ کنید. backup دیتابیس به‌تنهایی backup بایت‌های Storage نیست.

در **SQL Editor همان پروژه‌ای که سایت به آن متصل است**، کل فایل زیر را، از ابتدا تا انتها، در یک Query تازه قرار دهید و **Run** کنید:

```text
supabase/migrations/20260920000000_product_image_safety.sql
```

بخش‌ها را جداگانه اجرا نکنید. رمز، توکن، URL پروژه یا کلید خصوصی در SQL وارد نکنید. schema اولیهٔ کاتالوگ باید موجود باشد؛ نصب قبلی migration گالری الزامی نیست. این فایل جدول، RPC، trigger، policy، bucket و تأیید تراکنشی را پوشش می‌دهد؛ اجرای جداگانهٔ verify لازم نیست.

خروجی نهایی موفق باید شامل این موارد باشد:

- `products.id = text` و `product_images.product_id = text`؛ `product_images.id = uuid`.
- bucket به نام `product-images` با `public = true` و `file_size_limit = 8388608`.
- `inconsistent_primary_products = 0` و فهرست policyها.

اگر خطای schema، bucket خصوصی، constraint/index، trigger/rule یا ستون سفارشیِ ناشناخته، مجوز ارثی یا timeout دیدید، **ادامه ندهید و برای عبور از خطا، چک‌ها یا داده را حذف نکنید**. خطای قبل از `COMMIT` مانع ثبت تغییرات می‌شود؛ در صورت بازماندن تراکنش، `ROLLBACK;` لازم است. ناسازگاری مشخص باید بررسی شود، نه اینکه SQL قدیمی دوباره اجرا شود. اگر خطا فقط در رسید خواندنیِ بعد از `COMMIT` رخ داد، migration قبلاً ثبت شده و آن خطا rollback نیست.

## دقیقاً چه داده‌ای تغییر می‌کند؟

- هیچ `UPDATE` روی محصولات در مرحلهٔ migration اجرا نمی‌شود؛ **تمام ستون‌های محصولات، URLهای موجود، مقادیر فاصله‌ای و timestampها عیناً حفظ می‌شوند**. این برابری پیش از `COMMIT` با snapshot بررسی می‌شود. normalize کردن URL فقط برای نوشتن‌های آینده است، نه دادهٔ فعلی.
- ردیف گالری حذف نمی‌شود. برای URL فعلیِ بدون ثبت، ردیف legacy اضافه می‌شود؛ flag اصلی با URL فعلی هماهنگ می‌شود. فقط `is_primary` و در صورت تغییر واقعی آن، `updated_at` ردیف گالری ممکن است عوض شوند. بقیهٔ فیلدهای قبلی پیش از commit با snapshot مقایسه می‌شوند.
- URL دارای فاصله یا قالب قدیمی حفظ می‌شود؛ حفظ داده به معنی تأیید قابل‌نمایش‌بودن آن URL نیست. ویرایش بعدی از فرم محصول قواعد اعتبارسنجی جدید را اجرا می‌کند.
- فایل Storage حذف یا جابه‌جا نمی‌شود؛ `storage.objects` در migration تغییر داده نمی‌شود. تنظیم سقف آپلود و MIMEهای bucket موردنظر ممکن است تغییر کند، نه فایل‌های قبلی.
- bucket موجود اگر **خصوصی** باشد، اجرا متوقف می‌شود؛ بدون تصمیم آگاهانه عمومی نخواهد شد. bucket ناموجود به‌صورت عمومی ایجاد می‌شود. در bucket عمومی، داشتن URL برای دیدن فایل محصول غیرفعال کافی است؛ RLS محصول فعال فقط metadata را محدود می‌کند.
- URLهای واردشده legacy باقی می‌مانند. شباهت انتهای URL به مسیر Storage، دلیل مالکیت فایل نیست؛ migration آن را به upload قابل حذف تبدیل نمی‌کند.
- uniqueness سراسری نسخهٔ ۱ با uniqueness مسیر در هر محصول و uniqueness سراسری **فقط uploadهای مدیریت‌شده** جایگزین می‌شود. اگر دادهٔ قدیمی این قیود را نقض کند، اجرا متوقف می‌شود، نه deduplicate یا حذف.

## امنیت و اجرای مجدد

- کنترل نوع ستون‌ها، FK، PK، default شناسه، NOT NULLهای لازم، تعریف indexهای هم‌نام، RLS، helper نقش مدیر و trigger زمان ویرایش، قبل از قبول schema انجام می‌شود. ستون اضافی ناشناختهٔ گالری نیز رد می‌شود تا SELECT عمومی، دادهٔ خصوصی احتمالی را افشا نکند. تفاوت مشروع ولی سفارشی نیز ممکن است نیازمند بازبینی باشد؛ ادعای ترمیم هر schema دلخواه نداریم.
- همهٔ مجوزهای جدول، از جمله TRUNCATE و مجوزهای ستونی، از PUBLIC/anon/authenticated لغو می‌شوند؛ فقط خواندن موردنیاز بازگردانده می‌شود. مجوز ناامن ارثی که با لغو مستقیم حذف نشود، قبل از commit باعث توقف می‌شود.
- mutationهای گالری فقط از RPC مدیر انجام می‌شوند. helperهای خصوصی EXECUTE مرورگر ندارند. دو predicate مربوط به Storage برای اجرای policy قابل فراخوانی‌اند، اما برای غیرمدیر همیشه false برمی‌گردانند. owner/roleهای privileged دیتابیس مرز اعتمادند، نه کاربران مرورگر.
- توابع جدید `search_path = pg_catalog, pg_temp` دارند و به روابط/توابع برنامه با schema صریح ارجاع می‌دهند. RPCها نقش مدیر، تعلق تصویر، URL مورد انتظار و نتیجهٔ عملیات را کنترل می‌کنند.
- metadata دارای policyهای restrictive است. policyهای restrictive Storage فقط `product-images` را محدود می‌کنند؛ آزمون دسترسی anon در bucket دیگر نیز اجرا شده است.
- قفل محصول و قفل advisory مشترک ارجاع‌ها در تغییر تصویر/ثبت/بازنشستگی استفاده می‌شوند. قفل migration خواندن معمول فروشگاه را باز می‌گذارد، اما منتظر writerها می‌ماند؛ قفل طولانی به توقف با timeout منجر می‌شود. این طراحی جای تست رقابت واقعی Remote را نمی‌گیرد.
- اجرای دوم و سوم داده، timestampها، تنظیم bucket، صف cleanup، object metadata و تعریف policy/index/constraint را ثابت نگه می‌دارد؛ policy/تابع هم‌نام بازتعریف می‌شود، نه تکثیر. این idempotence معنایی است، نه ثابت‌ماندن OID داخلی policyهایی که drop/create می‌شوند.
- tombstoneهای cleanup برای جلوگیری از استفادهٔ مجدد مسیر باقی می‌مانند. حذف Storage نیازمند مدیر، tombstone و نبود ارجاع زنده است؛ URLهای encoded/signed/render نیز به‌صورت محافظه‌کارانه بررسی می‌شوند. مثبت کاذب ممکن است فایل اضافی را نگه دارد؛ حفاظت از عکس زنده مقدم است.

## تعارض با migrationهای قبلی و rollback

- `20260912000000_initial_schema.sql`: مبناست؛ نوع محصول **text**، helper مدیر و trigger زمان با آن تطبیق داده شده‌اند. داده و schema اصلی محصولات بازنویسی نمی‌شوند.
- `20260912000001_seed_catalog.sql`: این migration جدید آن را اجرا نمی‌کند. **seed را برای تعمیر دوباره اجرا نکنید**؛ UPSERTهای آن می‌توانند URL و سایر دادهٔ ویرایش‌شدهٔ محصول را بازنویسی کنند.
- `20260919000000_product_images.sql`: ارتقای رو به جلو از آن آزموده شده است. **بعد از نسخهٔ ۲ دوباره اجرا نشود**؛ به unique constraint قدیمی برای `ON CONFLICT` وابسته است و grants/policy/RPC قدیمی را بازمی‌گرداند. wrapper قدیمی انتخاب اصلی باقی مانده، اما نوشتن مستقیم پنل قدیمی عمداً مسدود است.
- CLI در نصب تازه باید migrationها را به ترتیب اجرا کند. SQL Editor تاریخچهٔ `supabase_migrations` را ثبت نمی‌کند. پس از اجرای دستی، پیش از هر `db push` آتی تاریخچه باید بررسی شود؛ اجازه ندهید فایل قدیمیِ ثبت‌نشده دوباره روی نسخهٔ ۲ اجرا شود. این تحویل تاریخچه را جعل یا repair نمی‌کند.
- تا **قبل از COMMIT**، خطا تغییرات همان تراکنش را برمی‌گرداند. بعد از آن down-migration خودکار و بی‌خطر نداریم: constraint، ACL، policy، trigger و دادهٔ گالری تغییر کرده‌اند. بازگشت نیازمند طرح restore از backup سازگار با نسخهٔ برنامه است؛ صرفاً drop کردن جدول‌ها یا اجرای v1 rollback نیست.
- حذف فیزیکی فایل در استفادهٔ بعدی پنل با rollback SQL بازگردانده نمی‌شود. Storage باید backup جداگانه داشته باشد.

## محدودیت عملیاتی باقی‌مانده

قطع شبکه ممکن است نتیجهٔ upload را نامعلوم کند. پنل همان شناسهٔ عملیات و preview را برای retry حفظ می‌کند؛ فایل مشکوک را حدسی حذف نمی‌کند. بستن مرورگر وسط upload ممکن است orphan باقی بگذارد. تست Remote بعد از فعال‌سازی هنوز انجام نشده و ادعای موفقیت آن نداریم.

گزارش ممیزی، متن کامل SQL و diff دقیق: `supabase/PRODUCT-IMAGE-MIGRATION-AUDIT-FA.md` و `supabase/product-image-safety-final-audit.diff`.

**هیچ commit، push، merge، workflow، deploy یا SQL روی Supabase اصلی اجرا نشده است.**
