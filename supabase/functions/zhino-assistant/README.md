# ZHINO — Supabase Edge Function «دستیار ژینو»

این تابع، تنها مسیر مجاز اتصال فروشگاه به مدل هوش مصنوعی است. کلید مدل در
**Secrets سوپابیس** می‌ماند و هرگز وارد مرورگر، بستهٔ نهایی یا این مخزن نمی‌شود.

```
مرورگر (فروشگاه)  ──POST──►  zhino-assistant (Deno)  ──►  مدل زبانی
   بدون هیچ کلید              AI_API_KEY اینجا             (OpenAI-compatible)
                                        │
                                        └── SELECT (کلید anon، تحت RLS)
                                            products · product_variants ·
                                            inventory · recipes · site_settings
```

تابع برای هر پرسش، «کارت اطلاعات فروشگاه» را از خودِ دیتابیس می‌سازد
(فقط ردیف‌های فعال و تنظیمات عمومی؛ همان چیزی که RLS به یک بازدیدکننده
اجازه می‌دهد). اگر این خواندن ممکن نبود، از متن کاتالوگی که فرانت‌اند
فرستاده استفاده می‌کند و در پاسخ اعلام می‌کند `knowledge` کدام بوده است.
هرگز `orders`/`order_items` خوانده نمی‌شود و هرگز `service_role` استفاده نمی‌شود.

## ۱. تنظیم Secrets

```bash
supabase secrets set AI_API_KEY="<کلید مدل>" AI_MODEL="<نام مدل>"
# اختیاری:
supabase secrets set AI_API_URL="https://api.openai.com/v1/chat/completions"
supabase secrets set ALLOWED_ORIGINS="https://zheno.devs.surf,https://<user>.github.io"
```

| Secret | الزامی | توضیح |
| --- | --- | --- |
| `AI_API_KEY` | ✅ | کلید مدل. فقط سمت سرور؛ هرگز در `VITE_*` نگذارید. |
| `AI_MODEL` | ✅ | نام مدل (یک مدل سریع و کم‌هزینه برای گفتگوی کوتاه کافی است). |
| `AI_API_URL` | — | پیش‌فرض: `https://api.openai.com/v1/chat/completions` (هر سرویس OpenAI-compatible). |
| `ALLOWED_ORIGINS` | — | پیش‌فرض `*`؛ در محیط واقعی دامنه‌های خودتان را بگذارید. |

`AI_API_KEY` می‌تواند از نوع `OPENAI_API_KEY` هم خوانده شود (سازگاری).

## ۲. استقرار

```bash
supabase functions deploy zhino-assistant
```

- `verify_jwt` پیش‌فرض روشن است؛ فرانت‌اند در حالت Supabase هدر
  `Authorization: Bearer <publishable key>` را می‌فرستد (همان کلید عمومی پروژه).
- تابع هیچ نوشتنی در دیتابیس ندارد و به هیچ جدولی دست نمی‌زند؛ فقط متن
  کاتالوگ را از فرانت‌اند می‌گیرد.

## ۳. تنظیم فرانت‌اند

کاری لازم نیست: اگر `VITE_SUPABASE_URL` و کلید عمومی پروژه تنظیم شده باشند،
فروشگاه خودش این تابع را روی
`<VITE_SUPABASE_URL>/functions/v1/zhino-assistant` صدا می‌زند. اگر Backend
اختصاصی خودتان را دارید، فقط آدرس آن را بگذارید:

```bash
VITE_ASSISTANT_API_URL=https://api.example.com/assistant/chat
```

اگر هیچ‌کدام تنظیم نشده باشد، صفحهٔ دستیار با «موتور محلی فروشگاه» کار می‌کند:
بدون هیچ درخواست شبکه‌ای، بر پایهٔ همان کاتالوگ و دستورهای واقعی (بدون ادعای
هوش مصنوعی).

## ۴. قرارداد API

| متد | پاسخ | کاربرد |
| --- | --- | --- |
| `GET` | `{ ok, configured, model, database }` | بررسی آماده‌بودن مدل و دسترسی دیتابیس؛ برای نشان «متصل/آفلاین» در صفحهٔ دستیار |
| `POST` | `{ reply, model, knowledge }` | پرسش کاربر |

بدنهٔ `POST`:

```json
{
  "message": "قیمت ژله انار چند است؟",
  "history": [{ "role": "user", "content": "سلام" }],
  "catalog": "متن فشردهٔ کاتالوگ فرانت‌اند (فقط اگر دیتابیس در دسترس نبود استفاده می‌شود)",
  "catalogSource": "database",
  "locale": "fa-IR"
}
```

`knowledge`: `database` (تابع خودش دیتابیس را خوانده) · `client` (از متن
کاتالوگ فرانت‌اند) · `none` (هیچ داده‌ای نبوده — UI به کاربر هشدار می‌دهد).

خطاها: `400` درخواست نامعتبر، `403` دامنهٔ ناشناس، `405` متد نادرست،
`413` بدنهٔ بزرگ، `429` سهمیهٔ پرسش، `501` پیکربندی‌نشده، `502` پاسخ
نگرفتن از مدل. فرانت‌اند در همهٔ این حالت‌ها به موتور محلی برمی‌گردد و به
کاربر هم شفاف می‌گوید که پاسخ از اطلاعات فروشگاه ساخته شده است.

## ۵. نکات امنیتی

- کلید مدل هرگز در `src/`، `VITE_*`، GitHub Secretsِ فرانت‌اند یا بستهٔ نهایی نمی‌آید.
- پاسخ تابع هیچ‌وقت کلید یا خطای خام سرویس‌دهنده را برنمی‌گرداند.
- محدودیت‌ها: پیام ۶۰۰ نویسه، بدنه ۲۴KB، کاتالوگ ۸۰۰۰ نویسه، تاریخچه ۸ نوبت،
  سهمیهٔ سادهٔ ضدسوءاستفاده (۲۰ پرسش در ۵ دقیقه برای هر IP در هر نمونه).
- خواندن فروشگاه با کلید anon انجام می‌شود (نفس RLS)؛ اگر بعداً بخواهید
  دستیار فقط بخشی از کاتالوگ را ببیند، همان policy ها را محدود کنید.
- `ALLOWED_ORIGINS` را در محیط واقعی روی دامنه‌های خودتان بگذارید
  (پیش‌فرض `*` فقط برای راه‌اندازی سریع مناسب است).
- برای سقف‌گذاری جدی‌تر، محدودیت نرخ را در سطح پلتفرم/دروازه هم فعال کنید.
- اگر Backend اختصاصی دارید، همان اصول را رعایت کنید: کلید سمت سرور،
  ورودی محدود، خروجی پاک‌سازی‌شده، و لاگ بدون دادهٔ حساس.
