# ZHINO — پودر ژله و کاستر

وبسایت فروشگاهی ژینو — ساخته شده با React + TypeScript + Vite + Tailwind CSS

## راه‌اندازی

```bash
# نصب وابستگی‌ها
npm install

# اجرای محیط توسعه
npm run dev

# ساخت نسخه نهایی
npm run build

# پیش‌نمایش نسخه نهایی
npm run preview
```

## ساختار پروژه

```
src/
  components/    # کامپوننت‌های مشترک
  pages/         # صفحات اصلی
  layouts/       # لایه‌های صفحه
  data/          # داده‌های محصولات و دستورها (داده‌های پایه، دست‌نخورده)
  services/      # سرویس‌ها (صدا، پرداخت و...) + لایه داده مشترک فروشگاه/پنل
  hooks/         # هوک‌های سفارشی
  context/       # کانتکست‌های React
  utils/         # توابع کمکی
  types/         # تایپ‌های TypeScript
  admin/         # پنل مدیریت (رابط، ناوبری، احراز هویت)
  components/assistant/  # دستیار ژینو (دکمهٔ شناور + محیط چت تمام‌صفحه)
  services/assistant/    # منطق دستیار: اطلاعات فروشگاه، موتور محلی، اتصال مدل
supabase/
  migrations/    # اسکیمای دیتابیس (RLS)
  functions/     # Edge Function «zhino-assistant» (پروکسی امن مدل)
```

## محصولات

### پودر ژله
- انار، توت فرنگی، هلو، تمشک، بلوبری، پرتقال، آناناس، آلبالو

### پودر کاستر
- موز، طالبی، توت فرنگی، کاکائو، هفت میوه، پرتقال، محلبی وانیلی

## پنل مدیریت (Admin)

- **ورودی:** سه پرچم کوچک و بی‌برچسب (🇮🇷 🇹🇷 🇮🇶) در انتهای نوار لینک‌های پایین فوتر؛
  کلیک روی آن‌ها صفحه ورود پنل را می‌گشاید.
- **مسیرها:** `/admin/login` (ورود) و `/admin/dashboard`، `/admin/products`،
  `/admin/orders`، `/admin/inventory`، `/admin/recipes`، `/admin/site-content`،
  `/admin/settings`.
- **احراز هویت:** دو حالت، بسته به پیکربندی:
  - **متصل به Supabase** (وقتی `VITE_SUPABASE_URL` و
    `VITE_SUPABASE_PUBLISHABLE_KEY` تنظیم شده باشند): ورود واقعی با حساب
    Supabase Auth (ایمیل + گذرواژه). پس از ورود، نقش مدیر با تابع
    `is_admin()` دیتابیس بررسی می‌شود و نشست در همان مرورگر بازیابی می‌شود.
  - **حالت نمایشی** (بدون پیکربندی): هیچ گذرواژه‌ای بررسی یا ذخیره نمی‌شود و
    رابط ورود همین را صریح می‌گوید.
  - برای بکند اختصاصی: `VITE_ADMIN_AUTH_MODE=api` همراه با `VITE_API_BASE_URL`.
- **داده‌های پنل — محصولات و موجودی:** در حالت متصل، مستقیم روی دیتابیس
  Supabase خوانده و نوشته می‌شوند (RLS فقط برای حساب مدیر اجازهٔ نوشتن می‌دهد).
  «حذف» هرگز ردیفی را پاک نمی‌کند؛ فقط `active = false` می‌شود تا سفارش‌های
  ثبت‌شده و تاریخچه سالم بمانند. در حالت بدون دیتابیس، همان overlay قبلی در
  localStorage همین مرورگر فعال است (کلیدها با پیشوند `zhino_admin_`):
  - `zhino_admin_catalog_v1` — ویرایش/افزودن/حذف/غیرفعال‌کردن محصولات + موجودی
  - `zhino_admin_orders_v1` — سفارش‌های ثبت‌شده از تسویه‌حساب (حالت بدون بکند)
  - `zhino_admin_recipes_v1` — ویرایش دستورها
  - `zhino_admin_content_v1` — متن‌های قابل‌ویرایش سایت
  - `zhino_admin_settings_v1` — آستانه ارسال رایگان، هزینه‌های ارسال، آستانه کم‌موجودی
- **داشبورد:** شش آمار زنده (جدید، آماده‌سازی، ارسال‌شده، تکمیل‌شده، مجموع فروش و کم‌موجودی) از همان snapshot سفارش/کاتالوگ خوانده می‌شوند. صفحهٔ اصلی لوگو، نوار وضعیت سفارش‌ها و launcherهای دایره‌ای مستقیم برای همهٔ بخش‌ها دارد؛ قیمت و تصویر از همان بخش محصولات با focus link باز می‌شوند. نمایش و ترتیب کارت‌ها فقط به‌عنوان ترجیح غیرحساس در localStorage همین مرورگر قابل تنظیم است و روی دسترسی یا دادهٔ اصلی اثر ندارد.
- **سفارش‌ها و تسویه‌حساب:** در حالت متصل، سفارش مهمان از طریق RPC
  `create_order` دیتابیس ثبت می‌شود (حساب کاربری لازم نیست): قیمت، هزینه ارسال
  و مبلغ نهایی را سرور از کاتالوگ و تنظیمات محاسبه می‌کند و موجودی را در همان
  تراکنش به‌صورت اتمی کم می‌کند؛ مرورگر نمی‌تواند قیمت را دست‌کاری کند یا از
  موجودی عبور کند. بخش «سفارش‌ها» پنل مدیریت همان ردیف‌ها را می‌خواند (RLS: فقط
  حساب مدیر) و تغییر وضعیت را روی دیتابیس ذخیره می‌کند. در حالت بدون دیتابیس،
  رفتار قبلی دست‌نخورده است: سفارش در localStorage همین مرورگر ثبت و از همان
  پنل مدیریت می‌شود (`zhino_admin_orders_v1`).
- **معماری:** فروشگاه فقط از `src/services/` (catalog, settings, content, recipes,
  orders) می‌خواند؛ داده‌های پایه در `src/data/` دست‌نخورده‌اند. اتصال بکند فقط
  تعویض بدنه توابع سرویس‌ها (fetch) است و نه بازسازی پنل یا فروشگاه.
  تا زمانی که مدیری تغییری ذخیره نکند، خروجی سایت دقیقاً مثل قبل است.

## اتصال پنل به دیتابیس Supabase

پنل مدیریت می‌تواند مستقیماً روی دیتابیس واقعی کار کند. این اتصال **اختیاری**
است: تا وقتی متغیرهای زیر تنظیم نشوند، سایت دقیقاً مثل قبل (کاتالوگ ثابت +
localStorage) کار می‌کند.

### ۱. متغیرهای محیطی

| متغیر | مقدار | توضیح |
|---|---|---|
| `VITE_SUPABASE_URL` | `https://<ref>.supabase.co` | آدرس پروژه (عمومی) |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_…` یا کلید anon | کلید عمومی؛ در مرورگر قابل انتشار است |

- **برای اجرای محلی:** این دو را در `.env` بگذارید (از `.env.example` کپی کنید).
- **برای انتشار روی GitHub Pages:** در مخزن → Settings → Secrets and variables
  → Actions → تب **Variables** این دو را با همان نام‌ها بسازید
  (`VITE_SUPABASE_URL`، `VITE_SUPABASE_PUBLISHABLE_KEY`). workflow انتشار
  آن‌ها را به build پاس می‌دهد.

> ⚠️ **هرگز** کلید `service_role` / `sb_secret_…` را در این متغیرها یا در کد
> نگذارید. آن کلید RLS را دور می‌زند. اگر برنامه چنین کلیدی ببیند، اتصال به
> دیتابیس را رد می‌کند و `npm run verify:supabase` هم در صورت commit شدن آن
> fail می‌شود.

### ۲. ساخت حساب مدیر

۱. در Supabase → Authentication → Users یک کاربر با ایمیل و گذرواژه بسازید.
۲. برای همان کاربر در `app_metadata` مقدار `{"role":"admin"}` ثبت کنید
   (Dashboard یا Management API). `is_admin()` همین مقدار را از JWT می‌خواند.
۳. ورود از `/admin/login` انجام می‌شود؛ حساب‌های بدون این نقش وارد پنل نمی‌شوند
   و حتی با نشست معتبر هم RLS هیچ نوشتنی به آن‌ها اجازه نمی‌دهد.

### ۳. دامنهٔ این فاز

| بخش | وضعیت |
|---|---|
| محصولات (افزودن/ویرایش/قیمت/وزن/تصویر/نمایش) | ✅ متصل به دیتابیس |
| موجودی (ذخیره از طریق RPC اتمی `set_inventory_stock`) | ✅ متصل به دیتابیس |
| ورود و نقش مدیر (Supabase Auth + `is_admin()`) | ✅ متصل |
| دستورها، متن‌های سایت، تنظیمات | ✅ متصل به دیتابیس (RLS؛ localStorage فقط fallback آفلاین) |
| سفارش‌ها (ثبت مهمان از طریق `create_order` + مدیریت در پنل) | ✅ متصل به دیتابیس |

### ۴. نکات ایمنی و رفتار مرزی

- **دامنه باید `https` باشد.** آدرس `http://` (به‌جز `localhost`) رد می‌شود، چون
  توکن نشست مدیر در هدر فرستاده می‌شود و در بستر بدون TLS افشا می‌شد.
- **دیتابیس مرجعِ نهایی است.** تا وقتی آخرین خواندن موفق از دیتابیس موجود است،
  فروشگاه فقط از همان داده‌ها استفاده می‌کند: محصولی که در دیتابیس غیرفعال شده
  از سبد حذف می‌شود (نه اینکه با داده‌های پایه «زنده» شود) تا قیمت یا موجودی با
  دیتابیس اختلاف پیدا نکند. فقط وقتی هیچ خواندن موفقی نداشته‌ایم، داده‌های پایهٔ
  سایت نمایش داده می‌شوند.
- **نوشتن‌ها هرگز بی‌صدا انجام نمی‌شوند.** اگر دیتابیس پیکربندی شده باشد اما در
  دسترس نباشد، پنل به‌جای ذخیره در localStorage خطا نشان می‌دهد؛ هیچ نوشتنی در
  دو جا (مرورگر و دیتابیس) تکرار نمی‌شود.
- **بدون پیکربندی، هیچ درخواستی به شبکه نمی‌رود** (تست خودکار این را تضمین
  می‌کند) — یعنی سایت فعلی تا زمان فعال‌سازی دست‌نخورده می‌ماند.
- **دسترسی به سفارش‌ها فقط از طریق RLS.** جداول `orders`/`order_items` نه برای
  مهمان‌ها و نه برای حساب‌های غیرمدیر قابل خواندن یا نوشتن‌اند؛ تنها مسیر
  نوشتنِ مهمان، خود RPC `create_order` است (security definer، با اعتبارسنجی
  سمت سرور). کلید `service_role` هرگز در فرانت‌اند نیست و اگر شناسایی شود
  کلید، اتصال رد می‌شود.

### ۵. رفتار در قطعی اتصال

اگر دیتابیس در دسترس نباشد، سایت با داده‌های پایه رندر می‌شود (صفحهٔ سفید
نمی‌شود)، آخرین snapshot قبلی حفظ می‌شود، و پنل مدیریت وضعیت «خطا در اتصال»
را نشان می‌دهد. هیچ نوشتنی هم بی‌صدا موفق گزارش نمی‌شود: اگر دیتابیس ذخیره را
رد کند، بنر خطا در پنل ظاهر می‌شود و مقدار از دیتابیس بازخوانی می‌شود.

## دستیار ژینو (فاز ۵ تا ۷)

- صفحهٔ مستقل: **`/assistant`** — دکمهٔ شناور ربات به همین صفحه می‌رود
  (پنجرهٔ Popup حذف شده است) و روی خود این صفحه تکرار نمی‌شود.
- از فاز ۷ این مسیر یک **محیط چت تمام‌صفحه و خلوت شبیه ChatGPT** است: بدون
  هدر و فوتر فروشگاه (بدون منو، پرچم و بخش‌های اضافی)، سربرگ سادهٔ Premium
  (نشان ژینو، «دستیار ژینو»، پیل ظریف وضعیت، «گفتگوی تازه» و «بازگشت به
  فروشگاه») و کادر نوشتن پایین صفحه با گوشه‌های نرم و دکمهٔ ارسال.
- محیط گفتگو فارسی و RTL، با تصویر ربات، پیام خوشامد کوتاه، پیشنهادهای
  آماده، حالت «در حال پاسخ‌گویی»، مدیریت پیام خالی/خطا و طراحی واکنش‌گرا.
- پاسخ‌ها همیشه از اطلاعات واقعی فروشگاه می‌آید: کاتالوگ، قیمت، موجودی و
  دستورهای رسمی روی بسته. اگر اطلاعاتی نباشد، دستیار صریح می‌گوید و چیزی
  از خودش نمی‌سازد.
- اطلاعات از **دیتابیس واقعی** خوانده می‌شود: محصولات و طعم‌ها، قیمت، موجودی،
  دستورهای تهیه و تنظیمات ارسال (همان جدول‌ها و همان RLS فروشگاه). اگر
  دیتابیس در دسترس نباشد، صادقانه به دادهٔ محلی فروشگاه برمی‌گردد و همان را
  در پیل وضعیت صفحه نشان می‌دهد.
- اتصال به مدل هوش مصنوعی از پشت سرور انجام می‌شود
  (Supabase Edge Function `zhino-assistant` یا Backend خودتان)؛ تابع Edge
  خودش دیتابیس را با کلید عمومی می‌خواند و **کلید API هیچ‌وقت در فرانت‌اند
  نیست**. اگر پیکربندی نشده باشد، دستیار با موتور محلی و بدون هیچ درخواست
  شبکه‌ای کار می‌کند.
- راهنمای کامل: [`ASSISTANT_AI.md`](./ASSISTANT_AI.md) و
  [`supabase/functions/zhino-assistant/README.md`](./supabase/functions/zhino-assistant/README.md).

## آماده‌سازی برای بکند

- مدل داده در `src/types/index.ts`
- لایه سرویس در `src/services/`
- برای اتصال به بکند، API calls را در `src/services/` اضافه کنید
- متغیرهای محیطی را از `.env.example` کپی کنید

## استقرار در GitHub Pages

- آدرس انتشار: `https://<user>.github.io/zheno-website/`
- در `vite.config.ts` مقدار `base` برابر `/zheno-website/` تنظیم شده است.
- استقرار با GitHub Actions انجام می‌شود (`.github/workflows/deploy.yml`):
  `npm ci` ← `npm run build` ← انتشار پوشه `dist`.
- در تنظیمات مخزن: Settings ← Pages ← Source باید روی **GitHub Actions** باشد.
- فایل `dist/404.html` به‌صورت خودکار از `index.html` ساخته می‌شود تا رفرش
  صفحه‌های داخلی (مثل `/products/...` یا `/cart`) صفحه خالی برنگرداند.
- فایل `public/.nojekyll` از پردازش Jekyll روی خروجی جلوگیری می‌کند.
- حالت بدون بکند: اگر `VITE_API_BASE_URL` خالی باشد، تسویه‌حساب به‌صورت
  محلی ثبت و تأیید می‌شود؛ با اتصال بکند، کاربر به درگاه پرداخت هدایت می‌شود.
